可以继续。我看了你 `prefill-baseline` 现在最新代码，这一版的并行逻辑已经真的接上了：

```text
chunk0 compute 完成
        ↓
GET0: Phone backend -> host
        ↓ stage_ready
        ├──────── Phone compute chunk1
        │
        └──────── GET0 payload -> PC
```

Meta 现在确实是在 `wait_stage_ready(task_id)` 返回后先启动 Phone 的 `i+1`，等 TX0/PC ADD 完了才启动 PC 的 `i+1`，最后把 `next_compute_complete=true`，下一轮就不重复计算。这个结构是对的。

不过你说“速度下降”，我看代码后，**下一步我建议先不要继续扩大流水，而是先把现在的全局 `GRAPH_COMPUTE ACK` 改掉。**

你目前 RPC 的：

```cpp
GRAPH_COMPUTE
GRAPH_RECOMPUTE
```

每一次都改成了：

```cpp
send_rpc_cmd(..., nullptr, 0);
```

也就是客户端每个 subgraph 都等手机真正算完才返回。

服务端相应地也是每次计算完：

```cpp
server.graph_compute(...);

send_msg(sock, nullptr, 0);
```



这虽然让 correctness 很清楚，但它把原先 RPC 的 fire-and-forget 变成了：

```text
每个 subgraph:

PC ── GRAPH ──► Phone
PC ◄──── ACK ─── Phone
       ↑
     等一次
```

你 decode 一 token 有很多 subgraph，所以这个同步粒度太细了。我认为这就是**当前速度下降的第一嫌疑**。

### 下一步：ACK 不放在每个 GRAPH 上，只在 GET 前做一次 fence

我们真正需要保证的只有：

> 在 transfer socket 开始 GET `ffn_down_chunk` 之前，compute socket 上对应 Phone graph 必须已经执行完。

根本不要求其他所有 graph 每次都 ACK。

所以改成：

```text
compute socket:

GRAPH_COMPUTE chunk0 ───►    // fire-and-forget
                           Phone compute0 ███████
SYNC/FENCE ──────────────►
                           等前面的 compute0 完成
◄──────────── ACK


transfer socket:

GET chunk0 ──────────────►
        tensor_get ███
              ↓ stage_ready
              ├── network0 █████████
              └── compute1 ███████████
```

这比现在合理得多。

## 而且你不用再新增一套 Meta proc

最简单就是把现在这个：

```cpp
static void ggml_backend_rpc_synchronize(ggml_backend_t backend) {
    GGML_UNUSED(backend);
    // this is no-op
}
```

真正实现起来。

RPC command 增加一个：

```cpp
RPC_CMD_SYNCHRONIZE
```

放最后面：

```cpp
RPC_CMD_SET_TENSOR_FROM_LOCAL_FILE,
RPC_CMD_SYNCHRONIZE,
RPC_CMD_COUNT,
```

比如：

```cpp
struct rpc_msg_synchronize_req {
    uint32_t device;
};
```

客户端：

```cpp
static void ggml_backend_rpc_synchronize(
        ggml_backend_t backend) {

    auto * rpc_ctx =
        static_cast<ggml_backend_rpc_context *>(
            backend->context);

    rpc_msg_synchronize_req request {};
    request.device = rpc_ctx->device;

    // 必须是 compute socket
    auto sock = get_socket(rpc_ctx->endpoint);

    RPC_STATUS_ASSERT(sock != nullptr);

    const bool status =
        send_rpc_cmd(
            sock,
            RPC_CMD_SYNCHRONIZE,
            &request,
            sizeof(request),
            nullptr,
            0);

    RPC_STATUS_ASSERT(status);
}
```

注意这里一定是：

```cpp
get_socket(...)
```

不是：

```cpp
get_transfer_socket(...)
```

因为我们就是利用：

```text
同一 compute socket 的顺序
```

来建立 barrier。

---

服务端给 `rpc_server` 加：

```cpp
bool synchronize(uint32_t device) {
    if (device >= backends.size()) {
        return false;
    }

    ggml_backend_synchronize(backends[device]);

    return true;
}
```

handler：

```cpp
case RPC_CMD_SYNCHRONIZE: {
    rpc_msg_synchronize_req request {};

    if (!recv_msg(
            sock,
            &request,
            sizeof(request))) {
        return;
    }

    if (!server.synchronize(request.device)) {
        return;
    }

    if (!send_msg(sock, nullptr, 0)) {
        return;
    }

    break;
}
```

严格来说，因为你的 `rpc_server::graph_compute()` 本身调用的是同步的：

```cpp
ggml_backend_graph_compute(...)
```

所以 server 能读到 `SYNCHRONIZE` 时，前面的 `GRAPH_COMPUTE` handler 本身就已经返回了；再调用一次 `ggml_backend_synchronize()` 相当于多加一道保险。


从 `GRAPH_COMPUTE/RECOMPUTE` 里删除。
