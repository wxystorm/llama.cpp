对，**可以直接沿用你 prefill 那种“同 endpoint、不同 role key” 的做法**。而且我觉得这次就按这个思路做最自然：

```text
192.168.x.x:50052_compute
192.168.x.x:50052_transfer
```

注意这只是 **socket map 的 key 不同**，真正 connect 的地址仍然都是同一个：

```text
192.168.x.x:50052
```

不过这次 decode 有一个必须一起处理的点：

> 不能只是创建第二 socket，然后让 `GET_TENSOR` 改走它。

因为你当前 `GRAPH_COMPUTE` 是**只发送、不等服务端完成响应**的。现在之所以正确，是因为 `GRAPH_COMPUTE` 和后面的 `GET_TENSOR` 在同一 socket 上，服务端天然按顺序处理。`GET_TENSOR` 当前确实使用 `ctx->sock`，而 graph compute 也是通过缓存的 `get_socket(endpoint)` 发出去。 

所以我建议这次第二 socket 按下面四步引入。

### 1. 把 `get_socket()` 改成按 role 缓存

你现在大概是：

```cpp
static std::shared_ptr<socket_t> get_socket(
        const std::string & endpoint) {

    static std::mutex mutex;
    std::lock_guard<std::mutex> lock(mutex);

    static std::unordered_map<
        std::string,
        std::weak_ptr<socket_t>> sockets;

    auto it = sockets.find(endpoint);

    ...
}
```

改成：

```cpp
enum class rpc_socket_role {
    COMPUTE,
    TRANSFER,
};

static std::shared_ptr<socket_t> get_socket_role(
        const std::string & endpoint,
        rpc_socket_role role) {

    static std::mutex mutex;
    std::lock_guard<std::mutex> lock(mutex);

    static std::unordered_map<
        std::string,
        std::weak_ptr<socket_t>> sockets;

    const std::string key =
        endpoint +
        (role == rpc_socket_role::COMPUTE
            ? "_compute"
            : "_transfer");

    auto it = sockets.find(key);

    if (it != sockets.end()) {
        if (auto sock = it->second.lock()) {
            return sock;
        }
    }

    std::string host;
    int port;

    if (!parse_endpoint(endpoint, host, port)) {
        GGML_LOG_ERROR(
            "Failed to parse endpoint: %s\n",
            endpoint.c_str());

        return nullptr;
    }

    if (!rpc_transport_init()) {
        return nullptr;
    }

    // 注意这里还是 endpoint 原来的 host:port
    auto sock = socket_t::connect(
        host.c_str(),
        port);

    if (sock == nullptr) {
        return nullptr;
    }

    // 每一条 TCP connection 都单独 HELLO
    if (!negotiate_hello(sock)) {
        return nullptr;
    }

    sockets[key] = sock;

    return sock;
}
```

然后保留两个简单 wrapper：

```cpp
static std::shared_ptr<socket_t> get_socket(
        const std::string & endpoint) {

    return get_socket_role(
        endpoint,
        rpc_socket_role::COMPUTE);
}

static std::shared_ptr<socket_t> get_transfer_socket(
        const std::string & endpoint) {

    return get_socket_role(
        endpoint,
        rpc_socket_role::TRANSFER);
}
```

这样你原来所有代码：

```cpp
get_socket(endpoint)
```

**完全不用改**，仍然都是 compute socket。

只有我们明确想放到通信线程的地方才调用：

```cpp
get_transfer_socket(endpoint)
```

这就跟你 prefill 的结构基本一样。

### 2. `ggml_backend_rpc_buffer_context` 保存 endpoint

目前 buffer context 只有类似：

```cpp
struct ggml_backend_rpc_buffer_context {
    std::shared_ptr<socket_t> sock;
    void * base_ptr;
    uint64_t remote_ptr;
};
```

因为以后 `GET_TENSOR` 要自己获取 transfer socket，所以给它加：

```cpp
struct ggml_backend_rpc_buffer_context {
    std::shared_ptr<socket_t> sock;

    std::string endpoint;          // 新增

    void * base_ptr;
    uint64_t remote_ptr;
};
```

创建 buffer 时现在是类似：

```cpp
new ggml_backend_rpc_buffer_context{
    sock,
    nullptr,
    response.remote_ptr
}
```

改成：

```cpp
new ggml_backend_rpc_buffer_context{
    sock,
    buft_ctx->endpoint,
    nullptr,
    response.remote_ptr
}
```

然后只修改 `GET_TENSOR`：

现在是：

```cpp
static void ggml_backend_rpc_buffer_get_tensor(
        ggml_backend_buffer_t buffer,
        const ggml_tensor * tensor,
        void * data,
        size_t offset,
        size_t size) {

    auto * ctx =
        (ggml_backend_rpc_buffer_context *) buffer->context;

    ...

    bool status = send_rpc_cmd(
        ctx->sock,
        RPC_CMD_GET_TENSOR,
        &request,
        sizeof(request),
        data,
        size);

    RPC_STATUS_ASSERT(status);
}
```

当前源码就是这种单 socket 路径。

改成：

```cpp
static void ggml_backend_rpc_buffer_get_tensor(
        ggml_backend_buffer_t buffer,
        const ggml_tensor * tensor,
        void * data,
        size_t offset,
        size_t size) {

    auto * ctx =
        static_cast<ggml_backend_rpc_buffer_context *>(
            buffer->context);

    rpc_msg_get_tensor_req request {};

    request.tensor = serialize_tensor(tensor);
    request.offset = offset;
    request.size   = size;

    // GET 专门走 transfer channel
    auto sock = get_transfer_socket(ctx->endpoint);

    RPC_STATUS_ASSERT(sock != nullptr);

    const bool status = send_rpc_cmd(
        sock,
        RPC_CMD_GET_TENSOR,
        &request,
        sizeof(request),
        data,
        size);

    RPC_STATUS_ASSERT(status);
}
```

于是：

```text
GRAPH_COMPUTE
GRAPH_RECOMPUTE
ALLOC
SET
...
        ↓
compute socket


GET_TENSOR
        ↓
transfer socket
```

第一阶段这么区分已经够了。

### 3. 手机 server 必须支持同时 accept 两条连接，而且共用同一个 `rpc_server`

这是最重要的服务端修改之一。

你现在 server 实际还是：

```cpp
while (true) {
    auto client_socket = server_socket->accept();

    rpc_serve_client(...);

    // 上一个连接退出以后才能 accept 下一个
}
```

也就是说当前主 compute socket 一直存在的话，第二个 transfer socket 根本无法进入正常处理。

这里要变成：

```text
listener
  │
  ├── compute socket  → thread A
  │
  └── transfer socket → thread B
```

但是有个很重要的坑：

**不能每个 socket 分别 new 一个独立 `rpc_server`。**

因为 `rpc_server` 里面保存着：

```cpp
buffers
stored_graphs
```

而反序列化 tensor 时还会验证：

```cpp
buffers.find(result->buffer)
```

这个 remote buffer 是否属于当前 server。 

所以应该是：

```text
                 一个 shared rpc_server
                         │
              ┌──────────┴──────────┐
              │                     │
compute connection            transfer connection
```

具体可以把：

```cpp
static void rpc_serve_client(
    ...,
    socket_ptr sock,
    const ggml_rpc_local_tensor_source * tensor_source,
    ...)
{
    rpc_server server(
        backends,
        cache_dir,
        tensor_source);

    ...

    server.get_tensor(...);
}
```

改成接收 server：

```cpp
static void rpc_serve_client(
        std::shared_ptr<rpc_server> server,
        socket_ptr sock) {

    ...

    server->hello(...);

    ...

    server->get_tensor(...);

    ...

    server->graph_compute(...);
}
```

然后 server startup 里：

```cpp
auto shared_server =
    std::make_shared<rpc_server>(
        backends,
        cache_dir,
        tensor_source);
```

accept：

```cpp
while (true) {
    auto client_socket =
        server_socket->accept();

    if (client_socket == nullptr) {
        fprintf(
            stderr,
            "Failed to accept client connection\n");

        return;
    }

    printf("Accepted client connection\n");
    fflush(stdout);

    std::thread(
        [shared_server, client_socket]() {

            rpc_serve_client(
                shared_server,
                client_socket);

            printf(
                "Client connection closed\n");

            fflush(stdout);
        }).detach();
}
```

这样两条连接看到的是**同一份 remote buffers 和 cached graphs**。

### 4. 这里必须加一个 compute ACK

这个是这次和你 prefill 最大的区别之一，也正是上一轮踩坑的根源。

当前 server：

```cpp
case RPC_CMD_GRAPH_COMPUTE: {
    ...
    server.graph_compute(input);
    break;
}
```

执行完成以后**不发送 response**。

客户端也只是：

```cpp
send_rpc_cmd(
    sock,
    RPC_CMD_GRAPH_COMPUTE,
    input.data(),
    input.size());
```

发送完就返回了。

在只有一条 socket 时没问题：

```text
compute socket:

GRAPH_COMPUTE
      ↓
手机真正 compute
      ↓
GET_TENSOR
```

因为 socket 顺序帮你同步。

但是拆两条以后会变成：

```text
compute socket:
GRAPH_COMPUTE
    ↓
客户端发送完成就返回


transfer socket:
GET_TENSOR
    ↓
可能比手机 compute 完成更早
```

这不行。

这次我反而**不建议再额外设计 RPC_CMD_SYNC**。

更简单的方式是：

> 让 `GRAPH_COMPUTE` 和 `GRAPH_RECOMPUTE` 本身返回一个 0-byte completion ACK。

server：

```cpp
case RPC_CMD_GRAPH_COMPUTE: {
    std::vector<uint8_t> input;

    if (!recv_msg(sock, input)) {
        return;
    }

    if (!server->graph_compute(input)) {
        return;
    }

    // 新增：
    if (!send_msg(sock, nullptr, 0)) {
        return;
    }

    break;
}
```

同样：

```cpp
case RPC_CMD_GRAPH_RECOMPUTE: {
    rpc_msg_graph_recompute_req request;

    if (!recv_msg(
            sock,
            &request,
            sizeof(request))) {
        return;
    }

    if (!server->graph_recompute(request)) {
        return;
    }

    // 新增：
    if (!send_msg(sock, nullptr, 0)) {
        return;
    }

    break;
}
```

客户端原来：

```cpp
send_rpc_cmd(
    sock,
    RPC_CMD_GRAPH_RECOMPUTE,
    &request,
    sizeof(request));
```

改成：

```cpp
send_rpc_cmd(
    sock,
    RPC_CMD_GRAPH_RECOMPUTE,
    &request,
    sizeof(request),
    nullptr,
    0);
```

`GRAPH_COMPUTE` 同样：

```cpp
send_rpc_cmd(
    sock,
    RPC_CMD_GRAPH_COMPUTE,
    input.data(),
    input.size(),
    nullptr,
    0);
```

这样：

```text
ggml_backend_rpc_graph_compute()
```

返回就真正代表：

```text
Phone graph 已执行完
```

而不是：

```text
GRAPH_COMPUTE command 已发出去
```

这一步非常关键。

而且你当前 Meta 本来就是 PC/Phone 两个 worker 同时调用 backend compute，再分别 wait，所以 Phone RPC worker 在这里阻塞到手机计算结束并不会破坏 PC/Phone 同时计算。

## 做完这一步以后先别并行

也就是说这一个 commit 做：

```text
compute socket + transfer socket
shared rpc_server
GRAPH_COMPUTE completion ACK
```

但你的 Meta 仍然：

```cpp
task_id = transfer_worker->enqueue(...);

status =
    transfer_worker->wait(task_id);

return status;
```

保持不变。

于是时间线还是：

```text
Phone compute0
████████████
            ↓ ACK

transfer socket GET0
            ██████████

                        Phone compute1
                        ███████████
```

只是通信已经成功搬到了独立 TCP connection。

**这一步连续生成完全正确以后，才真正做下一刀：**

```text
Phone compute0
████████████
            ↓ ACK
            ├── GET/stage/TX0 ─────────────
            │
            └── Phone compute1 ────────────
```

所以你刚才说的 prefill 方案是对的：**客户端完全可以继续采用 `_compute` / `_transfer` 两套 map key。** 这次真正需要额外谨慎的是服务端的共享 `rpc_server`，以及把 `GRAPH_COMPUTE` 的“完成”语义钉死，否则第二 socket 会把原本依赖 TCP 顺序获得的隐式同步弄丢。
