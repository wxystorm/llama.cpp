对，这个方向可以直接定下来，而且我建议**不要把它做成“Phone 另起一个 compute worker 等 condition_variable”那么复杂**。利用你现在已经有的两条 socket，可以做到更简单、也更快：

> **把 `SNAPSHOT` 命令插在 Phone 的 compute socket 上，严格排在 `compute chunk0` 和 `compute chunk1` 之间；transfer socket 只负责等待 snapshot slot READY 后把它发走。**

这样“本地 release”甚至不需要额外一次通知——**compute socket 自己的 FIFO 顺序就是 release 条件**。

你现在 Phone 服务端的 graph 执行本身是同步的：`graph_compute()` 只有 `ggml_backend_graph_compute()` 真正结束以后才返回，recompute 也是一样。 因此只要把命令顺序排成：

```text
compute socket:

GRAPH chunk0
SNAPSHOT slot0
GRAPH chunk1
SNAPSHOT slot1
```

Phone 实际执行必然是：

```text
compute0 ███████████
                   │
snapshot0           █   ← tensor_get 到独立 host slot
                    │
compute1             ███████████
                              │
snapshot1                     █
```

与此同时 transfer socket：

```text
GET_SNAPSHOT(slot0) ────── 等 READY ─── send slot0 ███████
                                      ||
                              compute1 ███████████
```

这就同时解决了三个问题：

```text
✓ 不再 GET 正在被下一 chunk 覆盖的原 tensor
✓ 不再需要 PC stage_ready RTT
✓ 不再需要 RPC fence RTT
```

你旧 `feat/rpc-local-model` 的思路确实已经有“独立 download socket + response header 后 snapshot callback”：buffer context 长期持有 upload/download socket，GET 收完 response header 后触发 callback，再收 body。([GitHub][1])

这次我们保留“snapshot 后才能覆盖原 tensor”的核心，但把 **snapshot-ready 的决定彻底留在手机本地**。

# 3. `SNAPSHOT_TENSOR` 是最关键的一步

这个命令**必须走 compute socket**。

实现：

```cpp
bool rpc_server::snapshot_tensor(
        const rpc_msg_snapshot_tensor_req & request) {

    if (request.device >= backends.size()) {
        return false;
    }

    if (request.slot >= 2) {
        return false;
    }

    struct ggml_init_params params {
        /* .mem_size   = */ ggml_tensor_overhead(),
        /* .mem_buffer = */ nullptr,
        /* .no_alloc   = */ true,
    };

    ggml_context_ptr ctx_ptr {
        ggml_init(params)
    };

    GGML_ASSERT(ctx_ptr != nullptr);

    ggml_tensor * tensor =
        deserialize_tensor(
            ctx_ptr.get(),
            &request.tensor);

    if (tensor == nullptr ||
        tensor->buffer == nullptr) {
        return false;
    }

    auto & slot =
        snapshot_devices[request.device]
            ->slots[request.slot];

    // 等这个 slot 上一次发送完成。
    {
        std::unique_lock<std::mutex> lock(
            slot.mutex);

        slot.cv.wait(lock, [&]() {
            return slot.state ==
                rpc_snapshot_state::FREE;
        });

        slot.state = rpc_snapshot_state::FILLING;
        slot.seq   = request.seq;

        slot.data.resize(request.size);
    }

    // -------------------------------------------------
    // 唯一允许读取原 tensor 的地方。
    //
    // 此时：
    // previous GRAPH 已经结束；
    // next GRAPH 还没有开始。
    // -------------------------------------------------

    ggml_backend_tensor_get(
        tensor,
        slot.data.data(),
        request.offset,
        request.size);

    {
        std::lock_guard<std::mutex> lock(
            slot.mutex);

        slot.state =
            rpc_snapshot_state::READY;
    }

    slot.cv.notify_all();

    return true;
}
```

这一步的安全性来自 **compute socket 顺序**：

```text
Phone compute socket handler:

GRAPH0
  ↓
ggml_backend_graph_compute()
  ↓ 真正结束

SNAPSHOT0
  ↓
ggml_backend_tensor_get()
  ↓ 完整复制 8KB

GRAPH1
  ↓
才允许覆盖原输出 tensor
```

所以根本不存在：

```text
tensor_get0
||
compute1
```

当前服务端 graph 就是同步执行以后才从 handler 返回，所以这个排序是硬保证。

# 4. transfer socket 的 GET 不再碰原 tensor

新增：

```cpp
bool rpc_server::send_snapshot(
        const rpc_msg_get_snapshot_req & request,
        socket_ptr sock) {

    if (request.device >= backends.size()) {
        return false;
    }

    if (request.slot >= 2) {
        return false;
    }

    auto & slot =
        snapshot_devices[request.device]
            ->slots[request.slot];

    const uint8_t * data = nullptr;
    size_t size = 0;

    {
        std::unique_lock<std::mutex> lock(
            slot.mutex);

        slot.cv.wait(lock, [&]() {
            // 正确 seq 已经 READY
            if (slot.seq == request.seq &&
                slot.state ==
                    rpc_snapshot_state::READY) {
                return true;
            }

            // seq 已经越过去，说明协议出错
            if (slot.seq > request.seq) {
                return true;
            }

            return false;
        });

        if (slot.seq != request.seq ||
            slot.state !=
                rpc_snapshot_state::READY) {
            return false;
        }

        if (slot.data.size() != request.size) {
            return false;
        }

        slot.state =
            rpc_snapshot_state::SENDING;

        data = slot.data.data();
        size = slot.data.size();
    }

    // -------------------------------
    // 注意：这里直接从 slot 发。
    // 不再额外 memcpy 一份 response。
    // -------------------------------

    const bool ok =
        send_msg(sock, data, size);

    {
        std::lock_guard<std::mutex> lock(
            slot.mutex);

        slot.state =
            rpc_snapshot_state::FREE;
    }

    slot.cv.notify_all();

    return ok;
}
```

这里我们故意不：

```cpp
std::vector<uint8_t> response = slot.data;
```

因为最终目标是最快。

直接：

```text
snapshot slot
     ↓
socket send
```

少一次 host memcpy。

# 5. Server handler

compute socket 会收到：

```cpp
case RPC_CMD_SNAPSHOT_TENSOR: {
    rpc_msg_snapshot_tensor_req request {};

    if (!recv_msg(
            sock,
            &request,
            sizeof(request))) {
        return;
    }

    // 不发 ACK。
    break;
}
```

注意：

> **绝对不要 `send_msg(..., nullptr, 0)`。**

否则又把一次 RTT 加回来。

transfer socket：

```cpp
case RPC_CMD_GET_SNAPSHOT: {
    rpc_msg_get_snapshot_req request {};

    if (!recv_msg(
            sock,
            &request,
            sizeof(request))) {
        return;
    }

    if (!server.send_snapshot(
            request,
            sock)) {
        return;
    }

    break;
}
```

`arm`：

```cpp
static bool ggml_backend_rpc_snapshot_arm(
        ggml_backend_t backend,
        const ggml_tensor * tensor,
        size_t offset,
        size_t size,
        uint32_t slot,
        uint64_t seq) {

    auto * rpc_ctx =
        static_cast<ggml_backend_rpc_context *>(
            backend->context);

    rpc_msg_snapshot_tensor_req request {};

    request.device = rpc_ctx->device;
    request.slot   = slot;
    request.seq    = seq;

    request.tensor = serialize_tensor(tensor);

    request.offset = offset;
    request.size   = size;

    // ------------------------------------------------
    // 必须走 compute socket。
    //
    // GRAPH0 -> SNAPSHOT -> GRAPH1
    // 的 FIFO 顺序全靠它。
    // ------------------------------------------------

    auto sock =
        get_socket(rpc_ctx->endpoint);

    RPC_STATUS_ASSERT(sock != nullptr);

    return send_rpc_cmd(
        sock,
        RPC_CMD_SNAPSHOT_TENSOR,
        &request,
        sizeof(request));
}
```

不要 ACK。

# 9. 最关键：Meta 怎么改

这里才是真正改变 pipeline 的地方。

你现在是：

```text
enqueue transfer
    ↓
RPC fence
    ↓
GET live tensor
    ↓
stage_ready
    ↓
start Phone chunk1
```

当前代码确实是在 transfer task 里 fence、安装 stage callback、copy，然后主线程 `wait_stage_ready()` 后启动 Phone `i+1`。 

新的 snapshot 路径改成：

```text
GET_SNAPSHOT task 提前挂起
        ↓
ARM_SNAPSHOT 放入 compute socket
        ↓
立即 enqueue Phone chunk1
```

具体顺序我建议这样：

```cpp
const uint64_t snapshot_seq =
    backend_ctx->next_snapshot_seq++;

const uint32_t snapshot_slot =
    snapshot_seq & 1;
```

`backend_ctx` 加：

```cpp

```

然后：

```cpp

            snapshot_seq]

            set_snapshot_read(

                snapshot_seq);

            const int64_t copy_start_us =

            ggml_backend_tensor_copy_async(

                bcj_dst.backend,
                node_src,

                false,
                0,

                ggml_time_us() - copy_start_us;
```

## 这次我建议分两个 commit，不要一口气改 Meta

第一个 commit **只做 RPC snapshot ring**：

```text
RPC_CMD_SNAPSHOT_TENSOR
RPC_CMD_GET_SNAPSHOT
2 slots
snapshot_arm proc
snapshot_read proc
```

先写个最保守测试，仍然：

```text
compute0
→ ARM snapshot
→ GET snapshot
→ 等 GET 完
→ compute1
```

确认输出 100% 正确。

第二个 commit 才把 Meta 从：

```cpp
wait_stage_ready();
start(phone, i + 1);
```

改成：

```cpp
snapshot_arm();
start(phone, i + 1);
```

并删掉这个 snapshot 路径上的：

```text
META_FENCE
stage_ready
```

旧的 fence/stage 代码先不要删，留作 fallback。

我尤其推荐这种实现，是因为它甚至不需要维护“graph0 completed / graph1 can start”这种额外 UID 依赖表。**你现有 compute socket 的命令顺序天然就是最可靠、最低开销的本地 dependency queue。** 当前 GRAPH 本来就是 fire-and-forget 客户端提交，而 Phone 服务端同步执行，所以非常适合这么干。

如果你现在准备开始改，**先做第一个 commit：只改 `ggml-rpc.h + ggml-rpc.cpp`，Meta 暂时一行不动。** 等这部分编译通过，我们再把 Meta 接过去，这样最稳。
