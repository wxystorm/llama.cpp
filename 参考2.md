可以，下一步就做 **`GRAPH_RECOMPUTE + SNAPSHOT_TENSOR` 融合**。不过这里有个关键点要先修正：

**不能只在服务端加一个融合 command，然后把 `snapshot_arm()` 换掉。**
因为你现在客户端的顺序是：`ggml_backend_rpc_graph_compute()` 已经先把 `GRAPH_RECOMPUTE` 发出去了，之后 Meta 才调用 `snapshot_arm()` 再发 `SNAPSHOT_TENSOR`。源码里确实是两个独立 RPC。 

所以第一版我建议做一个**改动较小的“延迟 RECOMPUTE + 在 snapshot_arm 时融合发送”版本**。这样暂时不用动 `ggml-backend-meta.cpp`，先验证收益。

## 目标

稳态从：

```text
GRAPH_RECOMPUTE
    ↓
Phone Wdown
    ↓
SNAPSHOT_TENSOR
    ↓
snapshot READY
```

变成：

```text
GRAPH_RECOMPUTE_SNAPSHOT
    ↓
Phone Wdown
    ↓
snapshot fill
    ↓
READY
```

`GET_SNAPSHOT` 那条 transfer socket 不动，仍然提前挂着等 READY。

而且只对：

```text
reuse == true
decode
ffn_down_chunk_*
```

启用。

**第一次 `GRAPH_COMPUTE` 仍走旧路径。**

## 2. 新 request 不再带 `rpc_tensor`

当前 `SNAPSHOT_TENSOR` 请求实际上把整个 `rpc_tensor` 又传了一遍：

```cpp
struct rpc_msg_snapshot_tensor_req {
    uint32_t device;
    uint32_t slot;
    uint64_t seq;
    rpc_tensor tensor;
    uint64_t offset;
    uint64_t size;
};
```

融合后：

```cpp
struct rpc_msg_graph_recompute_snapshot_req {
    uint32_t device;
    uint32_t slot;

    uint64_t graph_uid;
    uint64_t seq;

    uint32_t output_node;

    uint64_t offset;
    uint64_t size;
};
```

因为 server 已经通过：

```cpp
stored_graphs[device][graph_uid].graph
```

拥有完整缓存图，没必要再 deserialize 一遍 `rpc_tensor`。当前 `graph_recompute()` 本来就是通过 `graph_uid` 找 cached graph。

## 3. 把 snapshot 真正的数据抓取抽成 direct helper

你当前 `snapshot_tensor()` 的核心就是：

```text
等 slot FREE
→ FILLING
→ tensor_get
→ READY
→ notify_all
```



把这段抽出来：

```cpp
bool rpc_server::snapshot_tensor_direct(
        uint32_t device,
        uint32_t slot_id,
        uint64_t seq,
        ggml_tensor * tensor,
        uint64_t offset,
        uint64_t size) {

    if (device >= backends.size() ||
        slot_id >= 2 ||
        tensor == nullptr ||
        tensor->buffer == nullptr) {
        return false;
    }

    const uint64_t tensor_size =
        static_cast<uint64_t>(ggml_nbytes(tensor));

    if (offset > tensor_size ||
        size > tensor_size - offset) {
        return false;
    }

    rpc_snapshot_slot & slot =
        snapshot_devices[device]->slots[slot_id];

    {
        std::unique_lock<std::mutex> lock(slot.mutex);

        slot.cv.wait(lock, [&]() {
            return slot.state == rpc_snapshot_state::FREE;
        });

        slot.state = rpc_snapshot_state::FILLING;
        slot.seq   = seq;
        slot.data.resize(size);
    }

    const int64_t t0 = ggml_time_us();

    ggml_backend_tensor_get(
        tensor,
        slot.data.data(),
        static_cast<size_t>(offset),
        static_cast<size_t>(size));

    const int64_t t1 = ggml_time_us();

    if (RPC_DEBUG) {
        printf(
            "[RPC_SNAPSHOT_FILL] "
            "seq=%" PRIu64
            " bytes=%" PRIu64
            " tensor_get=%.3f ms\n",
            seq,
            size,
            (t1 - t0) / 1000.0);
    }

    {
        std::lock_guard<std::mutex> lock(slot.mutex);
        slot.state = rpc_snapshot_state::READY;
    }

    slot.cv.notify_all();

    return true;
}
```

然后原来的：

```cpp
rpc_server::snapshot_tensor(...)
```

保留前面的 deserialize，最后改成：

```cpp
return snapshot_tensor_direct(
    request.device,
    request.slot,
    request.seq,
    tensor,
    request.offset,
    request.size);
```

也就是说旧路径完全不废掉，方便 fallback。

## 4. Server 增加真正融合函数

class 声明增加：

```cpp
bool graph_recompute_snapshot(
    const rpc_msg_graph_recompute_snapshot_req & request);

bool snapshot_tensor_direct(
    uint32_t device,
    uint32_t slot,
    uint64_t seq,
    ggml_tensor * tensor,
    uint64_t offset,
    uint64_t size);
```

然后实现：

```cpp
bool rpc_server::graph_recompute_snapshot(
        const rpc_msg_graph_recompute_snapshot_req & request) {

    if (request.device >= backends.size() ||
        request.slot >= 2) {
        return false;
    }

    auto it =
        stored_graphs[request.device].find(
            request.graph_uid);

    if (it == stored_graphs[request.device].end() ||
        it->second.graph == nullptr) {
        return false;
    }

    ggml_cgraph * graph = it->second.graph;

    if (request.output_node >=
        static_cast<uint32_t>(graph->n_nodes)) {
        return false;
    }

    const int64_t t0 = ggml_time_us();

    const ggml_status status =
        ggml_backend_graph_compute(
            backends[request.device],
            graph);

    const int64_t t1 = ggml_time_us();

    if (status != GGML_STATUS_SUCCESS) {
        return false;
    }

    ggml_tensor * output =
        graph->nodes[request.output_node];

    if (output == nullptr) {
        return false;
    }

    const bool snapshot_ok =
        snapshot_tensor_direct(
            request.device,
            request.slot,
            request.seq,
            output,
            request.offset,
            request.size);

    const int64_t t2 = ggml_time_us();

    if (RPC_DEBUG) {
        printf(
            "[RPC_GRAPH_SNAPSHOT_SERVER] "
            "uid=%" PRIu64
            " node=%u "
            "seq=%" PRIu64
            " compute=%.3f ms "
            "snapshot=%.3f ms\n",
            request.graph_uid,
            request.output_node,
            request.seq,
            (t1 - t0) / 1000.0,
            (t2 - t1) / 1000.0);
    }

    return snapshot_ok;
}
```

这实际上就是把当前 `graph_recompute()` 的计算部分  和 `snapshot_tensor()` 的 fill 部分连起来。

# 6. 客户端：增加 pending fused graph

这是关键。

在：

```cpp
struct ggml_backend_rpc_context {
    std::string endpoint;
    uint32_t device;
    std::string name;
};
```

增加：

```cpp
struct rpc_pending_recompute_snapshot {
    std::mutex mutex;

    bool active = false;

    uint64_t graph_uid = 0;
    uint32_t output_node = UINT32_MAX;

    const ggml_tensor * tensor = nullptr;
};

struct ggml_backend_rpc_context {
    std::string endpoint;
    uint32_t device;
    std::string name;

    rpc_pending_recompute_snapshot pending_snapshot;
};
```

为什么不能 `thread_local`：

```text
GRAPH_RECOMPUTE
```

可能在 compute worker thread 调，

而：

```text
snapshot_arm
```

是 Meta 主线程调用。

所以一定放 backend context 里并加 mutex。

## 7. 只识别一个明确的 `ffn_down_chunk_` 输出

不要假定：

```cpp
graph->nodes[n_nodes - 1]
```

做 client helper：

```cpp
static int rpc_find_decode_ffn_down_output(
        const ggml_cgraph * graph) {

    int found = -1;

    for (int i = 0; i < graph->n_nodes; ++i) {
        const ggml_tensor * node =
            graph->nodes[i];

        if (node == nullptr) {
            continue;
        }

        const bool is_ffn_down =
            std::strncmp(
                node->name,
                "ffn_down_chunk_",
                15) == 0;

        const bool is_decode =
            node->ne[1] == 1;

        if (!is_ffn_down || !is_decode) {
            continue;
        }

        // 为了第一版安全：
        // 一个图里必须恰好找到一个候选。
        if (found != -1) {
            return -1;
        }

        found = i;
    }

    return found;
}
```

你现在 Phone 端 cached Wdown graph 的确基本都是 `nodes=4`，但不要硬编码 node 3。

# 8. `graph_compute()` 的 reuse 分支暂时“不发送”

当前 reuse 这里直接：

```cpp
send_rpc_cmd(
    sock,
    RPC_CMD_GRAPH_RECOMPUTE,
    ...);
```



改为：

```cpp
if (reuse) {
    const int output_node =
        rpc_find_decode_ffn_down_output(cgraph);

    if (output_node >= 0) {
        auto & pending =
            rpc_ctx->pending_snapshot;

        {
            std::lock_guard<std::mutex> lock(
                pending.mutex);

            // 正常路径这里不应该还有上一个 pending。
            GGML_ASSERT(!pending.active);

            pending.active      = true;
            pending.graph_uid   = graph_uid;
            pending.output_node =
                static_cast<uint32_t>(output_node);

            pending.tensor =
                cgraph->nodes[output_node];
        }

        if (RPC_DEBUG) {
            printf(
                "[RPC_GRAPH_DEFER] "
                "uid=%" PRIu64
                " output_node=%d tensor=%s\n",
                graph_uid,
                output_node,
                cgraph->nodes[output_node]->name);
        }

        return GGML_STATUS_SUCCESS;
    }

    // 不是目标 Wdown 图，保持原来的 GRAPH_RECOMPUTE
    ...
}
```

这里**只 defer cached Wdown graph**。

第一次：

```text
reuse=false
GRAPH_COMPUTE
```

完全保持不动。

# 9. `snapshot_arm()` 消费 pending，并一次发送融合 command

当前 `snapshot_arm()` 会构造完整 `rpc_msg_snapshot_tensor_req` 并发送 `SNAPSHOT_TENSOR`。

在它最前面加：

```cpp
static bool ggml_backend_rpc_snapshot_arm(
        ggml_backend_t backend,
        const ggml_tensor * tensor,
        size_t offset,
        size_t size,
        uint32_t slot,
        uint64_t seq) {

    auto * rpc_ctx =
        static_cast<ggml_backend_rpc_context *>(
            backend->context);

    uint64_t pending_uid = 0;
    uint32_t pending_output_node = UINT32_MAX;

    bool use_fused = false;

    {
        auto & pending =
            rpc_ctx->pending_snapshot;

        std::lock_guard<std::mutex> lock(
            pending.mutex);

        if (pending.active &&
            pending.tensor == tensor) {

            pending_uid =
                pending.graph_uid;

            pending_output_node =
                pending.output_node;

            pending.active = false;
            pending.tensor = nullptr;

            use_fused = true;
        }
    }

    auto sock =
        get_socket(rpc_ctx->endpoint);

    RPC_STATUS_ASSERT(sock != nullptr);

    if (use_fused) {
        rpc_msg_graph_recompute_snapshot_req request {};

        request.device =
            rpc_ctx->device;

        request.slot =
            slot;

        request.graph_uid =
            pending_uid;

        request.seq =
            seq;

        request.output_node =
            pending_output_node;

        request.offset =
            offset;

        request.size =
            size;

        const bool status =
            send_rpc_cmd_compact_small(
                sock,
                RPC_CMD_GRAPH_RECOMPUTE_SNAPSHOT,
                request);

        if (RPC_DEBUG) {
            printf(
                "[RPC_GRAPH_SNAPSHOT_CLIENT] "
                "uid=%" PRIu64
                " node=%u "
                "seq=%" PRIu64
                " bytes=%zu\n",
                request.graph_uid,
                request.output_node,
                request.seq,
                size);
        }

        return status;
    }

    // ===== 原 snapshot_arm 完整保留 =====
```

这里的：

```cpp
send_rpc_cmd_compact_small(...)
```

换成你刚刚推广后的**通用小 RPC helper 实际名称**即可。

新 request 只有几十字节，所以继续单次 `send_data()`。

## 10. 一定加一个 pending fallback

第一版调试的时候我不建议只写：

```cpp
GGML_ASSERT(!pending.active);
```

最终最好有 helper：

```cpp
static bool rpc_flush_pending_recompute(
        ggml_backend_rpc_context * ctx);
```

如果：

```text
pending.active
但 snapshot_arm tensor 不匹配
```

必须先把原来的：

```text
GRAPH_RECOMPUTE
```

补发出去。

否则某个特殊图没走 snapshot，就会被永远跳过计算。

逻辑：

```cpp
if (pending.active &&
    pending.tensor != tensor) {

    // copy graph_uid
    // clear pending
    // send normal RPC_CMD_GRAPH_RECOMPUTE
}
```

同样，如果下一次 `ggml_backend_rpc_graph_compute()` 开始时发现还有旧 pending，也先 flush。

这样即使识别条件哪次没对上：

```text
性能退回旧路径
```

而不是：

```text
计算直接缺失
```

这是 correctness 的保险。

## 最终实际时序

第一 token/首次 graph：

```text
GRAPH_COMPUTE
     ↓
Phone compute
     ↓
SNAPSHOT_TENSOR
     ↓
READY
```

保持原样。

稳定 decode：

```text
PC compute worker
    |
    | graph_compute(reuse)
    | 只记录 pending，不发包
    |
    v
transfer worker
    |
    | GET_SNAPSHOT(seq=N)
    |------------------------------> Phone transfer thread
    |                                wait READY
    |
main / snapshot_arm
    |
    | GRAPH_RECOMPUTE_SNAPSHOT
    |------------------------------> Phone compute thread
                                     graph compute
                                          ↓
                                     Wdown output
                                          ↓
                                     snapshot fill
                                          ↓
                                       READY
                                          |
Phone transfer thread <-------------------+
    |
    | raw 16KB
    v
PC
```

这和你现在的 snapshot pre-posted receive 机制仍然兼容。`send_snapshot()` 本身已经就是等待对应 `seq` 进入 READY。

### 我建议第一版就做到这里，不碰 `SET_TENSOR(ffn_norm)`

验证成功后，你应该看到 Phone 日志由：

```text
[graph_recompute]
[RPC_GRAPH_SERVER]
[RPC_SNAPSHOT_FILL]
```

变成：

```text
[RPC_GRAPH_SNAPSHOT_SERVER]
```

而 PC 每层：

```text
[RPC_GRAPH_DEFER]
[RPC_GRAPH_SNAPSHOT_CLIENT]
[RPC_SNAPSHOT_COMPACT_CLIENT]
```

最终仍然必须保持：

```text
reduce_to_primary=32
1->0 count=32
1->0 bytes=0.500 MiB
0->1 count=33
```

**通信数据量不会变，减少的是每层一个 RPC command / dispatch，以及整个 `SNAPSHOT_TENSOR` request。**

有一点要提前预期：这个第一版把真正的 Phone Wdown 启动点从原来的 `graph_compute()` 推迟到了 `snapshot_arm()`。两者之间目前应该很短，但如果实测 `1.1 → 反而略降`，不代表“融合没用”，而说明这个延迟抵消了 RPC 减少的收益。届时第二版就把 Meta 顺序调整成 **先 pre-post `GET_SNAPSHOT`，再立即发融合 command**，这样可以同时保留早启动和单 RPC。当前先用这一版验证最合适。
