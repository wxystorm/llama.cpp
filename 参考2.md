### 最小修改：只有“真正做流水的 GET”才走 transfer socket

这个比给所有 fallback 到处加 fence 干净得多。

你已经有：

```cpp
static thread_local
ggml_backend_rpc_stage_ready_callback_t
    rpc_stage_ready_callback = nullptr;
```



那它正好可以作为判断依据。

把现在：

```cpp
static void ggml_backend_rpc_buffer_get_tensor(
        ggml_backend_buffer_t buffer,
        const ggml_tensor * tensor,
        void * data,
        size_t offset,
        size_t size) {

        (ggml_backend_rpc_buffer_context *) buffer->context;

    request.size   = size;

```

改成：

```cpp
static void ggml_backend_rpc_buffer_get_tensor(
        ggml_backend_buffer_t buffer,
        const ggml_tensor * tensor,
        void * data,
        size_t offset,
        size_t size) {

    auto * ctx =
        static_cast<ggml_backend_rpc_buffer_context *>(
            buffer->context);

    rpc_msg_get_tensor_req request {};
    request.tensor = serialize_tensor(tensor);
    request.offset = offset;
    request.size   = size;

    bool status;

    if (rpc_stage_ready_callback != nullptr) {
        // -----------------------------------
        // Pipeline B 专用路径
        //
        // 前面 Meta 已经显式 rpc_fence()
        // 所以这里允许使用独立 transfer socket
        // -----------------------------------
        auto sock =
            get_transfer_socket(ctx->endpoint);

        RPC_STATUS_ASSERT(sock != nullptr);

        status = send_rpc_cmd_staged(
            sock,
            RPC_CMD_GET_TENSOR,
            &request,
            sizeof(request),
            data,
            size);
    } else {
        // -----------------------------------
        // 普通 GET
        //
        // 继续使用原 compute socket，
        // 保留 GRAPH -> GET 的隐式顺序
        // -----------------------------------
        status = send_rpc_cmd(
            ctx->sock,
            RPC_CMD_GET_TENSOR,
            &request,
            sizeof(request),
            data,
            size);
    }

    RPC_STATUS_ASSERT(status);
}
```

这个设计跟你现在的结构正好匹配。

因为 decode 专用 worker 里已经：

```cpp
rpc_fence(...);

set_stage_ready(
    ggml_backend_meta_stage_ready,
    &stage_context);

ggml_backend_tensor_copy_async(...);
```



所以那条线程调用 `get_tensor()` 时：

```cpp
rpc_stage_ready_callback != nullptr
```

自然走：

```text
transfer socket
```

而 prefill / 普通 fallback 没安装 callback：

```cpp
rpc_stage_ready_callback == nullptr
```

自然回到：

```text
compute socket
```

于是两类路径彻底分开：

```text
普通路径：
GRAPH ─► compute socket
GET   ─► compute socket
        保证顺序


Pipeline B：
GRAPH ─► compute socket
FENCE ─► compute socket
GET   ─► transfer socket
        ↓ stage_ready
TX0 || compute1
```

### 改完之后你应该先看 correctness

最重要的是第一 token top10 应该重新接近之前：

```text
top[0]: token=13398 logit≈19.2366
top[1]: token=797   logit≈14.7124
...
```

如果恢复，那就基本坐实是 **prefill 的跨 socket GET race**。

有一点别被日志迷惑：改完以后，prefill 的：

```text
[META_COPY] 1->0 node_30
```

可能又重新变成几百 ms。

这**不代表网络再次变慢**，因为普通 prefill GET 又回到了 compute socket，它可能会把前面 Phone graph 的等待时间吃进去。

我们真正应该继续观察的是 decode 专用路径：

```text
[META_FENCE] sg=1 ...
[META_COPY]  sg=1 ffn_down_chunk_0 ...
```

这里现在已经拆得比较干净了。你目前稳定后的数字大约：

```text
fence0 ≈ 15 ms
copy0  ≈ 18~20 ms

fence1 ≈ 8 ms
copy1  ≈ 21~24 ms
```

所以**真实的 Phone→PC GET 路径确实仍然偏慢**，但先把输出正确性恢复；之后我们再把这 20ms 拆成：

```text
GET request → response header
= tensor_get + RTT

response header → payload complete
= 真正的 8KB 网络接收
```

你现在的 `send_rpc_cmd_staged()` 已经天然有这个分界点，下一步很好测。
